# Codex/Claude Code 業界分析移行仕様

## 目的

Makeで動かしていた業界分析の2シナリオを、CodexとClaude Code中心の運用へ移す。

- シナリオ1: どのテーマで書くかを決める「トレンド候補生成」
- シナリオ2: 選ばれたテーマを記事化する「業界分析記事生成」

Makeのblueprintは、長いプロンプトと検索・整形・シート更新の分岐が混在していた。Codex移行後は、Makeの役割をそのまま再現するのではなく、以下に分ける。

- Codex: ニュース収集、検索クエリ設計、外部情報の裏取り、準備パック作成、レビュー、画像・WordPress反映
- Claude Code: 構造化メモ作成、記事HTML作成、レビューメモ作成
- Google Sheets: ステータス、パス、WordPress ID、画像フォルダ、X投稿管理

## Blueprintから移植する最重要点

## FIC業界分析の編集ポリシー

業界分析記事は、公表データや企業発表をただまとめるための記事ではない。読者がニュースを見た直後に持つ「で、どの企業に影響するのか」「どの指標を見ればよいのか」「いつ業績に出るのか」に答えることを最優先する。

- 事業紹介・政策説明・市場概況だけで終わらせない。
- 起点イベントから、恩恵候補、逆風候補、関連企業、業績ドライバー、先行指標、反対シナリオまで進める。
- 関連企業への直接発注や受注が未確認の場合でも、確度の高い仮説と確認条件を示す。無理に断定せず、`公式発表` `会社説明` `報道ベース` `調査会社予測` `FIC仮説` を分けて、投資家が使える形にする。
- ファクトの安全性を優先するあまり、ニュース要約で止めない。安全性は、確度ラベル、時間軸、先行指標、反対シナリオで担保する。
- FIC記事として読者に刺さるのは、「何が発表されたか」だけでなく「それでどの企業・業界に、どの時間軸で、どの指標を通じて波及するか」まで答える記事である。

### シナリオ1: トレンド候補生成

- 候補は最新ニュース起点にする。ただし原油、LNG、半導体、Rapidus/Tenstorrentだけに偏らせない。
- 日本マクロ、消費、金利、銀行、不動産、決算、設備投資、貿易、コモディティ、物流、AIクラウド/AIソフトウェアも拾う。
- Make版が拾えていたテーマの広さをCodex側に移すため、ニュース検索クエリは8本固定ではなく14本を基本にする。賃金/消費、金利/銀行/不動産、物流/EC/観光、地政学/エネルギー、企業決算/設備投資、AI/テックを必ず見に行く。
- 企業名を事前固定しない。検索結果に自然に出てきた固有名詞だけを使う。
- 高関心イベント枠を残す。主要決算、業績ガイダンス変更、大型設備投資、戦略提携、M&A、供給契約、工場建設・停止、輸出規制、政策支援、技術転換はB評価でも候補に残す。
- `trend_name` は短く強い見出しにする。`〜による〜への影響` のような弱い説明調を避け、起点イベント、制約条件、価格変化、政策/規制、業績ドライバーが一目で分かる語にする。
- AI関連は最低2件を候補に残す。1件はRapidus/Tenstorrent系でもよいが、もう1件はAIクラウド投資、データセンター投資、半導体IP、CPU/GPU需要、AIソフトウェア、データセンター電力・冷却など別軸にする。
- 重複判定は削除判定ではない。近いテーマでも、最新ニュースに強い具体イベントがあれば `duplicate_check=要確認` または `重複あり` として候補に残してよい。

### シナリオ2: 業界分析記事生成

- 記事化用の検索クエリは12本。役割は、トレンド定義2、波及経路2、恩恵企業2、逆風企業1、反証・リスク1、先行指標1、類似過去事例1、周辺業界/二次波及1。
- クエリ設計では、13セクション投入パックを埋めることを目的にする。特に、関連銘柄候補リストの `社名/コード/対象セグメント/売上比率または代替KPI/会社コメント/直接度`、サプライチェーン5層、先行指標3階層、期待・コンセンサス情報に届く語を入れる。
- 検索結果の採用順位は、公式IR、企業決算、公的統計、業界団体統計、主要メディアを優先する。
- Facebook、LinkedIn、Substack、個人ブログ、投資SNS、暗号資産系ニュース、旅行記事、テーマ不一致ページは中心根拠にしない。
- シナリオ1の企業例、driver_type、影響業種、影響方向は暫定値。記事化前に検索結果と一次情報で再評価する。
- 古いメモ値より、記事生成日に近い最新決算・最新先行指標を優先する。
- demand、order、backlog、revenue forecast、sales、profit、price、costを混同しない。
- 政策テーマは、確定事項と未確定・仮説を分ける。
- 新規事業発表や政策発表を起点に関連銘柄へ波及させる記事では、公式発表・会社説明・報道ベース・調査会社予測・FIC仮説を分ける。混在する場合は、序盤に「区分/内容/投資判断上の意味」の3列表を置く。
- 関連企業名は、正式受注・JV・サプライヤー発表がない限り「恩恵確定」ではなく「確認候補」として扱い、定量化は受注開示後であることを明記する。
- Codex投入パックでは、ファクト素材だけでなく公開記事の編集方針も渡す。タイトル案、読者が最初に知りたい問い、冒頭で答える結論、強く書いてよいこと、弱めるべきこと、禁止表現を `Claude向けコピペ用記事化指示` に入れる。
- 関連銘柄は、`直接恩恵` `確認候補` `周辺材料` `不採用候補` に分ける。直接受注・供給契約・サプライヤー選定が未確認なら、Claudeが読みやすさのために `直接恩恵` と言い換えないよう明記する。
- 周辺ニュースや類似事例は、起点イベントとの関係を `直接材料` `補強材料` `別テーマ` に分類する。既存工場の黒字化、過去類似案件、業界全体統計などを、今回イベントの直接成果のように扱わない。
- 市場全体指標を個社業績へ直結させず、中間変数を挟む。
- 反証条件、市場が織り込み済みの可能性、ボトルネックを必ず入れる。

### 記事見出しテンプレート

業界分析記事は、企業分析記事とは別の読み順にする。ただし、全記事で同じ見出しに固定しない。テーマを以下の3タイプに分け、読者の疑問に近い順番でH2を組む。

1. **新規事業・ニュース解説型**: 企業の新規事業発表、工場建設、提携、投資計画、M&A、政策採択など。`ニュースの概要と発生要因 → 影響経路 → 関連銘柄候補 → 業績ドライバー → 競争環境 → ボトルネック → 先行指標 → 3シナリオ → 投資家が見るポイント → まとめ → FAQ → 参照資料`。最初のH2では H3 `何が変化しているか / 構造的要因 / 循環的要因 / 政策・地政学要因` を置く。
2. **マクロ・テーマ記事型**: 金利、為替、半導体市況、原油高、防衛、インバウンド、AI電力需要など。`トレンドの概要と発生要因 → 影響経路 → 恩恵セクター → 主要企業で見るべきポイント → 逆風セクター → ボトルネック → 先行指標 → 3シナリオ → 反対シナリオ → 投資家が見るべきポイント → まとめ → FAQ → 参照資料`。最初のH2では H3 `何が変化しているか / 構造的要因 / 循環的要因 / 政策・地政学要因` を置く。
3. **企業群・業界比較型**: 特定業界の企業群を横比較する記事。`業界の現在地 → 収益構造と業績ドライバー → 主要企業の比較 → 勝ち筋の違い → 先行指標 → 3シナリオ → リスク → 投資家が見るべきポイント → まとめ → FAQ → 参照資料`。

- 企業分析記事のように、末尾に大きな `関連銘柄分析` / `関連テーマ分析` カードを必ず置かない。
- 関連銘柄は、原則として「恩恵を受けやすい業界・企業」「主要企業で見るべきポイント」の中で扱う。
- 関連テーマは、「投資家が見るべきポイント」または「まとめ」に自然に統合する。
- 既存記事URLが明示されていて読者導線として有用な場合だけ、参照資料前に短い内部リンク欄を追加してよい。
- 関連銘柄・関連記事は、起点イベントからのサプライチェーン、直接競合、代替技術、顧客/発注者、規制・政策対象、資本市場/金融取引のいずれかで接続理由を1文で説明できるものだけ公開本文に出す。
- 「同じ広い業種」「大型株」「FIC内に既存記事がある」「SEO上つなぎたい」だけの関連企業・関連記事は公開本文に出さない。候補として残す場合は内部メモに不採用理由付きで残す。
- 見出しは読者が迷わない一般名を優先する。テーマ固有名詞だけの見出しにしすぎない。
- H2は短い章タイトルにする。原則15字以内、長くても20字程度に収め、具体的な固有名詞・数値・比較軸はH3または本文冒頭に逃がす。
- H3はH2配下の判断軸として使う。H2を横並びに増やすのではなく、長くなる章はH3で階層化する。
- 記事冒頭は、30秒要約の前に「この記事で何がわかるか」を本文2段落以内で書く。見出しは付けず、1段落目で「何を起点に、どの業界・企業群へどう波及するか」、2段落目で「投資判断で見る確認順」を示す。
- `beginner-box` の見出し絵文字は維持する。概念・誤読防止・因果の噛み砕きは `💡 ワンポイント解説：...`、難用語・会計用語・業種固有KPIは `📘 用語メモ：...` として役割を分ける。
- 起点企業のプロジェクト数値と、周辺企業・同業他社・市場全体の確認指標を同じ表に混ぜない。別プロジェクトや別会社の数値を同じ章で扱う場合は、H3と表を分け、別プロジェクトであることを表直前に明記する。
- 末尾構造は既存FIC記事と揃え、FAQは `<div class="faq-section">...</div>` で囲み、その後に `<h2>参照資料</h2><ul><li>...</li></ul>` を置く。参照資料見出しを `参考資料` などに言い換えず、参照資料の後に空の `faq-section` を残さない。
- row83のような「特定企業の新規事業発表を起点に、周辺業界への投資インパクトを読む記事」は、マクロ・テーマ記事型ではなく新規事業・ニュース解説型を使う。

### Codexレビュー

1. ファクト、時点、因果、個社名、URL、schemaを確認する。
2. タイトル、冒頭、30秒要約、FAQ、schema description が読者の検索意図に近く、かつ本文のファクト区分より強くなっていないか確認する。
3. `直接恩恵` `確認候補` `周辺材料` が混ざっていないか確認する。正式受注・契約・供給関係がない企業を直接恩恵と書いていたら修正する。
4. 周辺材料を起点イベントの直接成果のように扱っていないか確認する。
5. 必要なら `codex_reviewed_article.html` を作る。
6. 画像作成前に本文レビューを完了する。
7. 画像を作成し、ローカル画像フォルダをシートに保存する。
8. WordPressは既存投稿IDを確認し、あれば必ずその投稿を更新する。投稿IDが空欄の場合のみ既存投稿検索を行い、見つからなければ新規作成する。
9. スラッグは一度決めてシートに入力されたら固定する。既存スラッグがある場合、Claude/Codexは新しいスラッグを再生成せず、schemaの `mainEntityOfPage` も既存スラッグに合わせる。

### 業界分析の画像作成方針

業界分析記事の本文内画像は、Codexレビュー後の最終HTMLを起点に、原則として**生成AI画像**で作る。単なる装飾画像ではなく、読者が画像だけを見ても「何が起点で、どの業界に効き、どの指標を見ればよいか」が分かる投資インフォグラフィックにする。

- 画像は生成AIでゼロベース作成する。参考画像、IR資料、記事中の表、既存メディア画像をそのまま模写しない。
- 参考画像は「情報設計の型」を見るために使う。具体的には、強いタイトル、因果フロー、追い風/注意点のブロック、見る指標の整理、短い日本語ラベル、大きな文字、読みやすい階層を参考にする。
- 参考画像と同じレイアウト、色、アイコン、地図、構図をコピーしない。テーマごとにオリジナルの構成へ組み替える。
- 画像内には、記事を読まなくても意味が通る文言を入れる。最低限、`タイトル`、`起点イベント`、`因果フロー`、`追い風`、`注意点`、`見る指標` を短い日本語で入れる。
- 画像内テキストは短く大きくする。長文説明や細かい数値表は入れない。日本語が崩れた場合、誤字や意味不明ラベルが残った場合は不採用として再生成する。
- 正確な売上・利益・構成比などの数値グラフは生成AI画像で作らない。表データから機械的に作るHTML/CSS/SVG/PNGを使う。
- 画像作成時点で、`AW: 画像格納フォルダ` にローカル画像フォルダのフルパスを必ず保存する。

#### 非AIグラフ・構造図の扱い

業界分析記事では、生成AI画像とは別に、必要に応じて非AIのグラフ・構造図を追加する。生成AI画像は概念理解、非AIグラフは数値理解と比較判断のために使い分ける。

- Claudeは、記事の流れを見て「どこに何の非AI図表があると理解しやすいか」を `industry_analysis_review_notes.md` に提案する。
- Claudeは、図表そのものを作らない。提案するのは、図表名、挿入位置、使う数値、出典、読者に伝える一言、実装優先度まで。
- Codexは、Claude提案と元データを確認し、HTML/CSS/SVG/PNGのいずれかで実装する。実装後は、数値整合、出典、スマホ表示、WordPress表示を確認する。
- 追加候補は原則1〜3個に絞る。読者が読み飛ばすだけの図表は入れない。
- 図表タイトルは、抽象的な比喩や強すぎる断定ではなく、「何を確認すべきか」「どの段階で業績に効くか」が分かる実務的な結論にする。
- 正確な数値を読ませるものは、生成AIではなく非AI図表にする。
- 構造図と詳細表を併用する場合は、原則として構造図を先に置き、その直後に詳細表を置く。先に全体像、次に細部の順に読ませる。
- 構造図と詳細表で段階番号・ラベルが食い違わないようにする。図が4段階なら表も4段階に合わせ、細かい補足は表の列や本文で説明する。
- 段階図を使う場合は、今回のテーマ・発表・政策が図のどの段階に当たるかを本文で必ず説明する。例: `今回の発表は1と2が具体化した段階で、3は受注開示、4は売上計上で確認する`。
- 図表が表の読み方を説明している場合は、原則として図表を表の上に置く。読者に「まず全体像、次に企業別詳細」の順で読ませる。

非AI図表の候補:

| 図表タイプ | 使う場面 | 例 |
|---|---|---|
| 横棒グラフ | 企業別・セグメント別の規模差を見せる | 主要企業の売上高、受注残、設備投資額 |
| 積み上げ棒/構成比 | 業界内の売上構成・需要構成を見る | 電力需要の内訳、用途別市場構成 |
| ウォーターフォール | 増減要因を分解する | 営業利益の前年差、コスト増減要因 |
| ロードマップ | 時間軸の階段を見せる | 政策決定、発注、建設、売上計上 |
| 感応度表/マトリクス | 価格・為替・金利などの前提差を見る | 原油価格×為替、金利×不動産利回り |
| 先行指標ダッシュボード | 今後見るべき指標を整理する | 受注残、価格指数、稼働率、PMI |

## 記事品質ゲート

- 冒頭で、個別企業分析ではなくテーマ波及分析であることが分かる。
- 1行サマリー、30秒要約、現在の水準表、FAQ、schemaの主旨が一致する。
- 市場指標と個社指標を混同していない。
- 強い数値、日付、政策、規制は出典名・時点・対象範囲がある。
- 現在値として使う数値は、記事生成日時点で古すぎない。
- 未来イベントは記事生成日より後のものだけ。
- 主要企業は正式社名・現行証券コードで書く。
- 主要企業として扱うなら、最低1つはIR/決算/公的統計/主要メディアの確認材料がある。
- 関連銘柄候補に、社名・コード・対象セグメント・売上比率または代替KPI・会社コメント・直接度・確認KPIがある。
- 関連銘柄が `直接恩恵` `確認候補` `周辺材料` `不採用候補` に分かれている。
- タイトル、冒頭、30秒要約が読者の検索意図に近く、かつ公式発表より強い断定になっていない。
- 周辺材料を起点イベントの直接成果のように扱っていない。
- サプライチェーンが最上流→中間→直接→間接→下流の5層で整理されている。
- 先行指標が市場マクロ/業界中間/個社の3階層に分かれている。
- 出典が強/中/弱に分類され、弱い出典を中心根拠にしていない。
- 反証条件とボトルネックがある。
- 読み飛ばされるだけのKPI羅列をしない。
- 弱い出典の数値をsummary-box、現在の水準表、FAQ、schemaの中心根拠にしない。

### 運用ルール

- フィルター対象はAZ列までとする。
- 旧本文や旧画像HTMLは残すが、新規作業では長文セルに依存しすぎず、作業フォルダとパスで追跡する。
- 画像を作成したら、必ずAW列に画像格納フォルダを書く。
- WordPress反映時はAL列の既存投稿IDを最初に確認し、IDがあれば更新する。IDが空の場合のみ既存投稿検索後に新規作成する。
- Q列のスラッグは固定値として扱う。Q列に値が入っている行では、記事再生成・レビュー・WP更新時にスラッグを変更しない。Q列が空欄の新規記事だけ、P列タイトルからスラッグを新規生成する。
- 業界分析では、読者が読み飛ばすKPI羅列を避ける。規模表は「何を判断するための数字か」が分かるものだけ残し、必要ならグラフや横比較に置き換える。
