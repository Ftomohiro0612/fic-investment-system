# 教訓即時反映の3層型（標準パターン）

**位置づけ**：段階4標準プロトコル「**定義→本作業→点検→教訓即時反映**」サイクルの**教訓即時反映の標準型**。Phase 5 移行の核心資産として、新subagent作成時・既存subagent改修時・本作業実走時に発見した教訓を「**ルール参照・教訓追跡・実装ゲート**」の3層に分離して反映することで、再現性（次回も同パターンで再発防止）を担保する。
**初版**＝2026-05-24（3861_oji_v4_pilot 縦ライン検証で L-021/L-022/L-023 の3事例が3層型で定着しFICが標準型として評価）。今後の事例で追補する。

---

## 1. 3層型の定義

| 層 | ファイル例 | 役割 |
|---|---|---|
| **層1：具体ルール** | 領域別ガイド（`docs/data_figure_lessons.md` / `docs/ai_image_lessons.md` / `docs/non_ai_structure_chart_lessons.md` 等） | 「**次に同じ作業をする時に何を守るか**」を具体ルールとして書く。後続の subagent / 人 が同じ領域の作業時に**ルール参照**する。 |
| **層2：教訓本体** | `docs/chat_workflows/_analysis/review_lessons_log.md` | 「**いつ・どこで・どう発見されたか・普遍性は**」を教訓として時系列で記録。L-NNN番号付き。後続の curation・蒸留・新subagent設計時に**教訓追跡**する。 |
| **層3：実装ゲート** | subagent定義（`.claude/agents/{role}.md`）／Skill（`.claude/skills/{skill}/SKILL.md`）／テンプレ（`wordpress/templates/*.html` 等） | 「**次回 subagent が起動した時に確実に実行する**」ゲートとして組み込む。subagentの挙動を実際に変える**実装ゲート**として機能。 |

### 3層分離の利点
- 段階3パイロット時代は教訓を1箇所に書いて終わりがちだったが、3層分離により「**ルール参照（層1）・教訓追跡（層2）・実装ゲート（層3）**」の役割が明確化。
- 新規 subagent作成時は層1+2でガイドを参照、改修時は層3で実装漏れを防ぐ、レビュー時は層2で教訓履歴を辿る、と各役割が独立して機能。
- §7ゲート対象は層3（`.claude/skills/` および `.claude/agents/` 編集はFIC承認）。層1・層2は §7対象外＝即時反映可。
- 「データ的一般化」（複数事例で初めて普遍性が見える教訓）はまず層2に記録、複数事例蓄積後に層1へ昇格、最後に層3に実装ゲート化、という**段階的昇格パス**が可能。

## 3. 3層型の柔軟運用ルール（L-026相当・全層必須ではない）

3層型は「全層必須」ではなく、**教訓の性質に応じて層を選ぶ**運用が正解。

### 3-1. 教訓の性質別マッピング

| 教訓の性質 | 適用する層 | 理由・例 |
|---|---|---|
| **具体的な作業ルール**（次回同じ作業時に守るべき手順・閾値・形式） | 層1＋層2＋層3（フル3層） | L-021/L-022/L-023。subagent 行動を変える＝層3必須・領域別ガイドへの追補＝層1・教訓履歴記録＝層2 |
| **メタ規律**（設計原則・運用透明性・自己規律） | 層2＋α（CLAUDE.md等のメタ条項） | L-024（設計判断は実装後の実証で更新）／L-025（bypass下でも規律維持）。subagent 行動を直接変えるものではなく、設計判断や運用態度に関わる |
| **データ的一般化**（1事例では普遍か個社固有か判別できない） | 層2のみ（要追加観察） | L-001（FY2026 OUM・FY2025 Kioxia の試算扱い）など。複数事例で普遍性が確認できたら層1へ昇格、subagent行動を変える必要が出たら層3へ昇格 |
| **手戻り・差し戻し対応の運用記録** | 層2のみ | reviewer差し戻しの個別対応履歴。普遍性は薄いが履歴として残す |

### 3-2. 層別の§7ゲート対象判定

- **層1**：`docs/` 配下＝§7対象外＝即時反映可（FIC内容確認のうえ反映）。
- **層2**：`docs/chat_workflows/_analysis/review_lessons_log.md`＝§7対象外＝即時反映可。
- **層3**：
  - `.claude/skills/` 配下＝§7ゲート対象＝**FIC承認必須**。
  - `.claude/agents/` 配下＝§7ゲート対象＝**FIC承認必須**。
  - テンプレ（`wordpress/templates/*.html`）＝§7対象外だがFIC内容確認推奨。

### 3-3. 段階的昇格パス

1事例の教訓は**層2のみ**で記録（curation判定＝要追加観察）→ 複数事例で普遍性が確認できたら**層1へ昇格**（具体ルール化）→ subagent行動を変える必要が出たら**層3へ昇格**（実装ゲート化）、というパスが標準。

## 4. C'案基準（即時反映可 vs 段階4送り）

教訓を Skill / guide / template / agent定義 へ反映する判定基準（FIC合意 2026-05-22・C'案）。段階4 curation でも同じ基準で運用する。

### 4-1. 即時反映してよい
- **論理的に根拠づく原則**（1事例でも論理的に普遍性が明らか）
- **repo＋実物（公開HTML/一次資料）の両ソースで裏が取れた普遍ルール**（1事例でも昇格して安全）

### 4-2. 段階4へ送る
- 複数事例で初めて普遍性が見える**“データ的一般化”**（1事例では普遍か個社固有か判別できないもの）

### 4-3. §7ゲート対象＝`.claude/skills/` / `.claude/agents/` 配下のみ
- 上記配下の編集はFIC承認が必要
- `chapter_design_guide.md`・`wordpress/templates/`・本ログ・`docs/` 配下は§7対象外（FIC内容確認のうえ反映で可）

### 4-4. 判定例

| 事例 | C'案判定 | 反映先 |
|---|---|---|
| L-005（反証＝観測パターン閾値） | 論理的原則 → 即時反映 | chapter_design_guide |
| L-006（予想範囲の明示） | 条件付き普遍ルール → 即時反映 | factual-handling §3＋template |
| L-008（文体基調＝です・ます） | 普遍ルール → 即時反映 | writing-style §5 |
| L-002（IFRSラベル） | 両ソース裏取り済み普遍ルール → 即時反映 | factual-handling §3 |
| L-007（ハイパースケーラCapEx） | データ的・文脈依存 → 新規Skill変更せず（記事内のみ反映） | 段階4で再検討 |
| L-021/L-022/L-023 | 論理的原則＋両ソース裏取り済み → 即時反映（3層フル） | 各事例参照 |
| L-024/L-025（メタ規律） | 論理的原則＋両ソース裏取り済み → 即時反映（層2＋α・CLAUDE.md） | review_lessons_log + CLAUDE.md |

## 5. 適用ガイドライン（段階4以降の subagent 展開時）

新subagent（例：researcher_industry／scout／theme_scout／videographer／x_writer）作成時の標準プロトコル「**定義→Phase 0→本作業1本→点検→教訓即時反映**」の最後のフェーズで、本書を参照して以下を判断：

1. **教訓の性質を判定**（具体ルール／メタ規律／データ的一般化／運用記録）→ §3-1マッピング
2. **適用する層を決定**（フル3層／層2＋α／層2のみ）
3. **C'案基準で即時反映可否を判定**（§4）
4. **§7ゲート対象か確認**（§3-2）
5. **層1・層2は commit／層3は FIC承認待ち提案**（3段階フロー：起草→壁打ち→FIC承認）
6. **3層反映完了後、本書に新事例として追記**（参照型を蓄積）

### 段階4以降の他ロール作成時のチェックリスト

新subagent定義v1起草時：
- [ ] 既存の3事例（L-021/L-022/L-023）を参照型として読んだか
- [ ] 当該ロールが扱う領域に既存の層1具体ルール（領域別ガイド）があるか確認
- [ ] 既存ガイドの不足箇所を Phase 0 で発見したら、§3-1マッピングで層配分を判断
- [ ] 普遍性が確実な教訓のみ層3まで反映、判別不能なものは層2のみ（要追加観察）
