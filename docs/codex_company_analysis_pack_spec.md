# Codex 企業分析パック準備 指示書（汎用版）

このドキュメントは、FIC企業分析記事フローにおいて、Codex（または同等のPDF直読オペレーター）が **どの企業についても再現可能な形** で「Claude投入用パック」を準備するための仕様書です。

特定企業ごとの依頼ファイル（例: `work/company_analysis/<コード>_<企業名>/CLAUDE_CODE_FIC_INSTRUCTIONS.md`）はこの仕様書を踏襲した上で、企業固有の論点（業種特有のKPI、注意点、引用URL）を追加する位置づけです。

Make旧フローの設計思想、PDF要約・Serper検索・統合分析メモ・記事生成プロンプトの読解メモは `docs/make_company_analysis_blueprint_findings.md` を参照してください。

---

## 0. 目的とスコープ

- Make生成済み要約に依存せず、Codexが**シートに貼られたPDF URLを直接読み取り**、Claudeが企業分析記事と統合分析メモを書くための原材料を整える。
- 出力は2ファイル（`pdf_summary.md` と `claude_input_pack.md`）に固定する。Claudeはこの2ファイル以外の準備物には依存しない設計とする。
- 数値は**一次情報優先・出典明記・未開示は未開示と書く**を絶対ルールとする。

## 1. 成果物（必ず作成する5ファイル）

### 1.1 Codex作成（準備パック）

| ファイル | 役割 | 入力源 |
|---|---|---|
| `work/company_analysis/<コード>_<社名>/pdf_summary.md` | PDF**直読**による要約。Make要約・外部報道は混入させない。 | スプレッドシート該当行に貼られたPDF URL（決算説明資料、中期経営計画、統合報告書、必要に応じて決算短信・有報） |
| `work/company_analysis/<コード>_<社名>/claude_input_pack.md` | Claudeへの依頼文＋基本情報＋PDF要約＋Web補足＋記事構成案＋表データ＋禁止表現＋参照リンク をまとめたパッケージ | `pdf_summary.md` ＋ 公式IRページや会社プレスリリース等の補足Web情報 |

ファイル冒頭には**作成日、作成者、入力源URLリスト、Make要約不使用宣言**を必ず書く。

### 1.2 Claude作成（記事化・レビュー）

| ファイル | 役割 | 入力源 |
|---|---|---|
| `work/company_analysis/<コード>_<社名>/claude_integrated_memo.md` | 統合分析メモ（新14章構成、`docs/claude_integrated_memo_lessons.md` 第2章準拠） | Codex の `pdf_summary.md` ＋ `claude_input_pack.md` のみ |
| `work/company_analysis/<コード>_<社名>/claude_article.html` | 公開記事HTML（`wordpress/templates/company_analysis_template.html` 準拠） | 同上 |
| `work/company_analysis/<コード>_<社名>/claude_review_notes.md` | **Claude記事作成時のレビューメモ**。判断に迷った点・Codex側／FICレビューで再確認すべき点を構造化して残す | 記事作成中の自己観察 |

`claude_review_notes.md` は記事や統合メモには含めない**内部補助資料**として位置づける。記事作成中に「判断に迷った」「資料間で数値が揺れていた」「一次情報で要確認」と感じた点を**その場で記録**し、後段のCodexレビューやFIC編集レビューが効率化される設計。

`claude_review_notes.md` の標準セクション:

- 資料間の数値差異
- 参考試算の根拠（ROE・利益率など、会社開示値ではないもの）
- 計算方法の選択（分母選択、丸めなど)
- 一次情報で要確認の項目
- 公開報道との照合が必要な項目
- 上流市場規模の追加抽出余地
- 競合比較先の選定根拠
- 画像作成プレースホルダ
- 完了サマリー（カテゴリ別件数）

### 1.3 役割境界（Claude / Codex）

Claudeは**統合メモ・記事HTML・レビューメモの3点セット作成**に専念し、Codexは**PDF直読・準備パック作成・成果物レビュー・画像作成・画像挿入・WordPress反映・公開判断**を担う。それぞれの強みを生かす役割分担。

| 工程 | Claude | Codex |
|---|:---:|:---:|
| PDF直読・要約 | — | ○ |
| `pdf_summary.md` / `claude_input_pack.md` 作成 | — | ○ |
| `claude_integrated_memo.md` 作成 | ○ | — |
| `claude_article.html` 作成 | ○ | — |
| `claude_review_notes.md` 作成 | ○ | — |
| 非AIグラフ/数値図表の候補出し | ○ | — |
| シート反映（パス＋ステータス） | ○ | — |
| Claude成果物のレビュー（レビューメモ起点） | — | ○ |
| 非AIグラフ/数値図表の作成・挿入 | — | ○ |
| 画像作成・挿入 | — | ○ |
| WordPressへのアップロード・更新 | — | ○ |
| 公開判断 | — | ○ |

**越境禁止**:

- Claudeは画像作成・WP反映を行わない（API操作・画像生成を Codex に任せる）。
- Claudeは、記事の理解を助ける**非AIグラフ/数値図表の候補**を `claude_review_notes.md` または記事内コメントで提案してよい。ただし実際のグラフ画像・SVG・HTML図表の作成、数値検証、WordPress挿入は Codex が行う。
- Codexは記事文章の執筆を行わない（レビュー観点での修正指摘や数値差し替え依頼は可）。

**例外**:

- ユーザーが明示的に指示した場合のみ、上記の境界を越える。
- 軽微なテキスト修正（誤字・表記揺れ）は Codex 側で直接行ってよい。

### 1.4 シート連携：パス＋ステータスのみ（新標準）

Claude側成果物（メモ・記事HTML・レビューメモ）は**リポジトリ内のファイルが真実のソース**とし、シートには**ファイルパスとステータスのみ**記録する。シートに本文全文をコピーする運用は廃止する。

**理由**:

- シートの可読性向上（巨大セルで横スクロールが多発しない）
- 真実のソースの単一化（シート⇔リポジトリの二重管理を避ける）
- Git による完全な版管理が可能
- Codex／FIC編集レビュー側は、シートからパスを読んでリポジトリの該当ファイルを直接参照する

**シート記録項目（`企業分析` シートの場合）**:

| 列 | 役割 | 書き込む値 |
|---|---|---|
| `A` | Codex依頼/次アクション | 短い指示文（例: `Claude出力ファイル作成済み。Codexレビューして。`） |
| `AB` | Claude出力_統合メモ | `work/company_analysis/<コード>_<社名>/claude_integrated_memo.md` のパス文字列 |
| `AD` | Claude出力_記事本文 | `work/company_analysis/<コード>_<社名>/claude_article.html` のパス文字列 |
| `AS` | レビュー担当メモ | 短いステータス文＋`claude_review_notes.md` のパス |
| `AP` | ステータス | `Codexレビュー待ち` 等の状態ラベル |

**実行スクリプト**:

`scripts/sheets/update_sheet_row.mjs` に `--path-mode` フラグを追加済み（2026-05-14）。

```bash
node scripts/sheets/update_sheet_row.mjs \
  --key <key.json> \
  --sheet-id <sheet-id> \
  --tab "企業分析" \
  --row <行番号> \
  --memo work/company_analysis/<dir>/claude_integrated_memo.md \
  --article work/company_analysis/<dir>/claude_article.html \
  --memo-col AB --article-col AD \
  --skip-date --skip-status \
  --path-mode
```

`--path-mode` 指定時は、ファイル内容ではなくパス文字列をセルに書き込む。ファイルの存在は事前検証する。

追加オプション（任意）:

- `--review-col AS --review "claude_review_notes.v2.md 作成済み..."`: レビューメモ列へ短文記録
- `--action-col A --action "Claude出力ファイル作成済み..."`: 次アクション列へ短文記録
- `--status-col AP --status "Codexレビュー待ち"`: ステータス列上書き
- `--skip-date`: 作業日列の書き込みをスキップ
- `--skip-status`: ステータス列の書き込みをスキップ

**移行方針**:

- 既存案件で全文書き込み済みのもの（例: 出光5019 v1/v2）は遡及更新不要。次回更新時にパスモードへ移行する。
- 新規案件はパスモード標準で運用する。
- シート側の自動列（`AC` 統合分析メモ／`AE` 記事本文）は、Claude記事を読み込んで処理する WordPress 側スクリプトの動作確認が必要。現状の自動列処理がパスモードに未対応の場合、Codexが**画像挿入・WordPress反映時**にパス→ファイル内容の読み替えを行う。

## 2. `pdf_summary.md` の標準構成

各PDFごとに以下のブロックを揃える。資料数は最低2、推奨3（決算説明資料・中期経営計画・統合報告書）。

```
## N. <資料名> 要約

### 3行サマリー
- 当期実績の結論
- 翌期計画または会社方針の結論
- 投資家として最も重要な利益変動要因

### 業績とセグメント
（数値と前年比を明記。会計基準・定義差があれば該当行にラベル）

### 翌期（または計画年度）見通し
（前提市況、計画値、配当、CAPEX、財務目標）

### 投資家が見るべきKPI・論点
（先行指標、感応度、稼働率、特定案件など）
```

各セクション末尾に、**出典資料名＋確認日**（最低限 `(決算説明資料 2026-05-09)` 程度）。可能ならページ番号も付ける。

### 2.1 必須抽出データ（業種非依存）

PDFに記載があれば、必ず以下を抽出してリスト化する。**ないものは「資料非開示」と明記**。

#### 損益関係（直近2-3期分の推移）
- 売上高、営業利益、経常利益、税前利益、当期純利益
- 営業利益＋持分法投資損益（日本基準）／金融費用除き税引前損益（IFRS）など、会社が独自に用いる主要利益指標
- 在庫影響、一時要因、特別損益の内訳
- 会計基準（日本基準／IFRS／米国基準）と適用開始期

#### 過年度5年推移パック（Make比較で不足しやすい項目）
- 直近期だけでなく、最低4期、可能なら5期分の主要業績推移を作る。急回復・高利益率・赤字転落・一時損失などを記事で説明する場合は必須。
- 対象項目は、売上高、営業利益、営業利益率、純利益、ROE、営業CF、主要セグメント利益、会社が重視するKPI（受注高、受注残、販売台数、稼働率、会員数、粗利率など）を業種に合わせて選ぶ。
- 過去データは統合報告書・有価証券報告書・決算短信・決算説明資料のヒストリカルデータを優先する。古い資料の数値を使う場合は、対象年度・会計基準・組替有無を明記する。
- 記事で「特殊高水準」「構造的改善」「過去最高」「回復途上」と書けるかを判断できるよう、単年値ではなく時系列で示す。
- 取得できない場合は「過年度5年推移は会社資料で未取得」「KPIは過去分非開示」など理由を残す。

#### ビジネスモデルの数式分解
- Claude投入前に、その企業の売上・利益が何の掛け算で動くかを1つ以上の式で整理する。
- 例: `売上 = 数量 × 単価 × 稼働率 × 為替`、`利益 = 売上 × 粗利率 - 固定費`、`請負売上 = 受注残 × 進捗率`、`金融収益 = 債権残高 × 利ざや - 信用コスト`、`広告売上 = 利用者数 × 広告単価 × 表示回数`。
- 数式は厳密な会計式でなくてよいが、記事の読者が「何を見れば業績が動くか」を理解できる粒度にする。
- 会社資料に明示された分解を優先し、Codex側の整理である場合は「構造理解用の整理」と明記する。

#### ビジネスモデル類型・売上性質の分解
- 数式だけでなく、売上・利益の性質を類型で分ける。例: 受注生産型、継続課金型、スポット販売型、在庫販売型、開発売却型、金融・利ざや型、保守/サービス型、広告/手数料型。
- 類型ごとに、売上比率・利益比率・資産比率・受注残比率など、会社開示またはCodex計算で出せる比率を付ける。比率が取れない場合は `比率非開示` とし、定性的な重要度だけ残す。
- 類型ごとに「先行指標」「利益率を動かす変数」「リスクの出方」を1行で整理する。例: 受注生産型は受注残・進捗率・粗利率、開発売却型は含み益・売却時期・金利/キャップレート、継続課金型は会員数・解約率・ARPU。
- 会社資料に明示された分類を優先する。Codexが便宜的に分類する場合は、固定比率を推測で置かず、`Codex整理（比率は会社非開示）` と明記する。

#### セグメント別の損益と売上
- **セグメント別売上高**（前年比含む）— 業績の主柱比率が掴めるため最重要
- セグメント別利益（前年比、計画値、要因分解）
- 会社がセグメント利益または事業利益を開示している場合は、売上高だけの表で終わらせず、利益額・利益率・利益構成比を同じ表または隣接表で必ず提示する。
- 会社が用途別・製品別売上だけを開示している場合は、公開記事で `セグメント別` と呼ばず、`用途別売上構成` `製品別売上構成` などに言い換える。表直下に `利益・利益率は会社非開示` と明記する。
- セグメント別の数量・単価・スプレッド（記載があれば）

#### セグメント・地域・事業別の構成比%
- 絶対額だけでなく、売上・営業利益・受注・資産・地域売上などの構成比をCodex側で事前計算して提示する。
- 例: `セグメント利益A 1,000億円（全社営業利益の50%）`、`海外売上3,000億円（売上の30%）`、`主力事業の利益貢献率70%`。
- 構成比の分母（連結売上、全社営業利益、調整前セグメント利益合計、受注高合計など）を必ず明記する。調整額・消去が大きい場合は、分母を2種類出すか、構成比を参考値として扱う。
- セグメント名称が資料間で変わる場合は、旧新区分の対応をメモし、単純比較しない。

#### 売上・利益グラフ用データ
- 表だけでは規模感が読み取りにくい場合に備え、売上高・営業利益・セグメント利益・用途別売上のグラフ化に使えるデータを、Claude投入パックへ表形式で残す。
- 正確な数値を示すグラフは、生成AI画像ではなく、表データから機械的に作るHTML/CSS/SVG/PNGを使う。生成AI画像は文字崩れ・数値崩れが起きるため、売上高・利益・構成比を読ませる用途には使わない。
- セグメント利益が開示されている企業では、`売上最大の事業` と `利益最大の事業` が違うかを確認し、違う場合は記事本文で投資判断上の論点として扱う。
- セグメント利益が非開示の企業では、用途別・製品別の売上グラフに限定し、必要に応じて会社全体の `売上高・営業利益推移` グラフを併用する。

#### 財務指標
- ROE、ROIC、自己資本比率、DEレシオ、ネット有利子負債
- 過去3-5期の推移（推奨）
- 計画年度の目標値と現状値の距離

#### 株主還元
- 配当（実績／計画／配当方針）
- 自社株買い（金額／取得済／枠）
- 総還元性向、配当性向、累進配当の有無

#### 物量・設備・組織
- 生産能力、処理能力、販売能力（業種固有の単位）
- 主要拠点数（工場、店舗、SS、営業所）
- 従業員数、グループ会社数
- 地域別売上構成、製品別売上構成

#### サービス・プロダクトKPI
- MAU、WAU、DAU、有料会員数、課金率、ARPPU、継続率、解約率、広告主数、取引社数など、売上の数式分解に直接入るKPI
- タイトル数、提供国数、海外提供本数、配信作品数、提携パートナー数など、事業の広がりを示すKPI
- KPIがPDF内にグラフのみで出ている場合も、読み取れる範囲で数値・時点・注記を残す
- 会社がKPIを非開示にしている場合は「資料非開示」と明記し、記事では周辺KPIで代替できるかをメモする

#### 顧客・取引先・案件固有名詞パック
- セグメント別に、主要顧客層、発注者カテゴリ、テナント/取引先カテゴリ、代表案件名、代表製品/サービス名、用途、地域を整理する。
- 会社が実名開示している場合のみ、顧客名・発注者名・提携先名・テナント名を記載する。会社開示がない場合は、報道から推測で社名を書かず、`会社開示では名称非開示` と残す。
- 代表案件・プロダクトは、記事で固有名詞密度を上げるため、最低3件、複合業態では5-8件を目安に拾う。例: 大型工事名、新車種名、新工場名、主要ゲームタイトル、主要ブランド、主要施設名、共同開発先。
- 各固有名詞には、対応セグメント、収益への効き方（売上/利益/受注/将来オプション）、進捗段階、出典URL、確認日を付ける。
- 固有名詞を入れる目的は「読者が事業の実体を掴むこと」であり、会社業績への寄与が未確認のものは、寄与額を断定しない。

#### 開発体制・人的リソース
- 研究員数、開発者数、クリエイター数、スタジオ数、開発拠点、職種構成、採用数、平均年齢など、競争力を説明する人的資本KPI
- グループ会社や主要子会社の開発体制が業績ドライバーに直結する場合は、親会社IRだけでなく子会社公式サイト・採用サイト等の一次情報も確認する
- 数値が検索結果・採用ページ・会社紹介資料で異なる場合は、時点の新しい公式情報を優先し、古い数値は採用しない

#### 上流市場規模・業界KPI
- PDF内で特定された業績ドライバーに対応する上流市場規模を追加取得する
- 例: 広告事業なら国内広告費・国内動画広告市場、ゲーム事業なら国内/世界モバイルゲーム市場、IP事業ならアニメ産業市場・配信市場・キャラクター商品市場
- 取得する各市場指標には、数値、対象年、前年比、予測年、出典URL、確認日を付ける
- 業界団体・公的統計・会社/グループ公式調査を優先し、調査会社・報道は推計ラベルを付ける
- 成長テーマを記事に入れる場合は、そのテーマに対応する個別市場規模・投資額・CAGR・制度上限・導入容量などを最低1つ確認する。例: データセンター、半導体投資、洋上風力、AIサーバー、EV充電、住宅着工、医療費、広告市場など。
- 外部環境が利益率や売却益に効く場合は、関連する金利・利回り・価格指数・市況指標を数値で置く。例: 政策金利、長期金利、キャップレート、建設物価指数、原材料価格、運賃指数、在庫水準。
- 会社への影響が一次情報で直接確認できない外部指標でも、会社の用途・顧客層・製品説明と自然につながり、複数の外部情報で裏付けられる場合は、`高確度推定` または `業界構造からの推定` として記事本文に採用してよい。根拠が弱い場合のみ「外部環境の確認指標」「補助情報」に留める。

#### 外部金融・不動産・資本市場指標
- 業績ドライバーが金利・不動産市況・資本市場に影響される場合、会社の主要地域ごとに、政策金利、長期金利、為替、信用スプレッド、キャップレート、賃料、空室率、取引利回り、株式市場指標を確認する。
- 優先出典は、中央銀行、統計機関、規制当局、取引所、公的統計、業界団体、会社資料。公的ソースで取れない不動産キャップレート等は、JLL/CBRE等の専門レポートを `専門レポート` と明記して補助利用する。
- `現状値 / 直近変化 / 対象地域 / 対象資産 / 会社への効き方 / 波及ラグ` を表で出す。外部指標と会社利益の関係が未確認なら、`会社影響は未確認、確認指標として使用` と書く。
- 海外事業が大きい企業では、日本国内指標だけで済ませず、売上・利益・資産の大きい地域の指標を優先して取る。

#### 労働供給・人口/人材制約指標
- 労働集約型、専門人材依存、店舗/現場/物流/介護/建設/IT開発など人員制約が利益率に効く業種では、人材供給の外部指標を取る。
- 例: 就業者数、技能者数、年齢構成、欠員率、有効求人倍率、賃金指数、採用単価、時間外労働規制、外国人労働者数、資格者数、2030年/2035年などの長期推計。
- 優先出典は、官公庁、労働統計、業界団体、会社統合報告書。報道や民間推計を使う場合は `推計` と明記する。
- 記事では「人手不足」と一般論で済ませず、数値・時点・対象職種を置き、どのKPI（受注消化、店舗運営、粗利率、外注費、開発速度）に効くかを書く。

#### 価格改定・コストイベント
- 原材料、資材、部材、エネルギー、物流、人件費などのコストが業績を動かす場合、一般的な価格指数だけでなく、直近の価格改定イベントを確認する。
- 取得項目は、対象品目、改定額/改定率、実施日、対象地域、発表主体、出典、会社への直接影響の有無。例: 鋼材値上げ、生コン改定、電力料金改定、半導体価格、海上運賃、賃上げ率。
- 会社自身の価格転嫁・販売価格改定が開示されていれば最優先で使う。業界ニュースは補助情報として使い、会社への直接影響が未確認なら `業界環境、会社影響未確認` と明記する。
- 価格イベントは、上流環境マップ・リスク表・3シナリオ予測に接続できる形で残す。

#### 推定・仮説の採用方針（有用性重視）
- 一次情報で会社への直接影響が明示されていなくても、複数の信頼できる外部情報、業界構造、会社の用途/顧客/製品説明から**確度高く推定できる因果**は、記事素材として残す。
- その場合は `確定事実` と `推定/仮説` を分け、`高確度推定` `業界構造からの推定` `報道/統計に基づく仮説` のようにラベルを付ける。
- 推定の確度は3段階で付ける。
  - `高`: 会社資料に用途・顧客層・製品が明示され、外部指標との接続が業界構造上かなり自然。
  - `中`: 会社資料の直接記載は薄いが、複数の業界統計・専門紙・競合資料で同じ構造が確認できる。
  - `低`: 単一報道・一般論・類推に近い。記事本文では中心根拠にせず、確認論点に留める。
- `高` または `中` の推定は、本文で「〜とみられる」「〜につながりやすい」「〜が確認指標になる」の形で採用してよい。`非開示` だけで済ませない。
- 推定を採用する場合は、根拠を最低1つ書く。例: 会社開示の用途、業界統計、顧客業界の在庫/価格/投資動向、競合資料、専門紙報道。
- 金額・利益インパクトの数値化は、会社開示または計算根拠がある場合に限る。根拠が弱い場合は、方向感・ラグ・見るべきKPIに留める。

#### 業界内部の因果メカニズムパック（最重要）
- Claude投入前に、主要ドライバーごとに「外部指標が動いた」だけで止めず、**業界内部で何が起き、会社のKPIへどう変換されるか**を因果チェーンとして整理する。
- 各チェーンは最低4段階で書く。標準形は `上流イベント → 業界内部の行動/制約 → 会社が見る先行KPI → 売上/利益項目 → 波及ラグ`。
- 例: `メモリ価格上昇 → 自動車OEM/部品メーカーが安全在庫を積み増す → 水晶デバイスのスポット需要・受注が増える → 稼働率/製品ミックスが改善 → 0-2Qで営業利益率に反映`。
- 例: `防衛予算増額 → 防衛装備品・通信/測位/レーダー関連の調達案件が増える → 高信頼部品の受注機会が増える → 特殊用途品の数量/単価が上がる → 1-4Qで売上に反映`。
- 因果チェーンには、必ず「誰が行動するか」を入れる。例: OEM、Tier1、通信キャリア、データセンター事業者、官公庁、病院、建設発注者、広告主、販売代理店、消費者など。
- 会社への影響が一次情報で直接確認できない場合も、業界内部メカニズムとして有用で、上記の確度が `高` または `中` なら記事本文で採用してよい。その場合は `高確度推定` `業界構造からの推定` と明記し、断定ではなく「〜とみられる」「〜につながりやすい」と書く。
- 確度が `低` のチェーンは `会社影響は未確認、仮説チェーン` と明記し、記事本文では中心根拠にせず、`確認すべき論点` または `補助的な見方` として扱う。
- 各チェーンに「反証条件」を1つ置く。例: `価格上昇でも顧客在庫が既に高い場合は受注増につながらない`、`政策予算増でも対象装備に自社部品が使われなければ波及しない`。
- `claude_input_pack.md` には、以下の表を必ず入れる。

| チェーン名 | 上流イベント/指標 | 行動する主体 | 業界内部メカニズム | 会社KPI | 業績への波及 | ラグ | 反証条件 | 確度/根拠 |
|---|---|---|---|---|---|---|---|---|
| 例: DRAM価格と安全在庫 | DRAM価格上昇 | 自動車OEM/Tier1 | 安全在庫積み増し | 受注・稼働率 | 売上/利益率上振れ | 0-2Q | 顧客在庫が高い | 中 |

#### マクロ・業界外部指標の網羅パック
- PDF内の主要ドライバーに対応して、会社資料外のマクロ・業界指標を最低5件、外部環境依存が大きい企業では8-12件取得する。
- 取得対象は、需要温度計（PMI、鉱工業生産、設備投資、住宅着工、広告費等）、市場規模/CAGR、政策予算・補助金・規制値、設置数/普及率、価格指数、在庫水準、金利/為替、技術代替トレンドを含める。
- 公的統計・業界団体・規制当局を優先し、調査会社や専門紙を使う場合は `推計` `専門紙` `報道ベース` と明記する。
- 取得した外部指標は、単独で羅列せず、上の「業界内部の因果メカニズムパック」または「先行指標パック」のどちらかに必ず接続する。

#### 構造危機・過去赤字経験パック
- 直近が好調な企業でも、過去5-10年で赤字・大幅減益・構造改革・大型減損・競争激化を経験している場合は、その原因を1行で整理する。
- 目的は過去の失敗紹介ではなく、現在の強気シナリオが崩れる条件を見つけること。記事では「構造リスク」「反証条件」「下振れシナリオ」に接続する。
- 例: `過去赤字の主因: 中国/台湾勢の低価格攻勢 → 価格下落 → 稼働率低下 → 固定費負担増` のように、こちらも因果4段階で書く。

#### 先行指標パック（Make比較で不足しやすい項目）
- Claude投入前に、各業績ドライバーについて「指標名」だけでなく、**現状数値・時点・前年差/前月差・出典URL・会社業績への効き方・波及ラグ**まで取得する。
- 先行指標は最低5件、複合業態や外部環境の影響が大きい企業では8-12件を目安にする。取得できない場合は、空欄にせず `一次情報なし` `有料統計のみ` `報道ベースのみ` など理由を残す。
- 先行指標は以下の6種類に分けて拾う。
  - **需要指標**: 販売台数、出荷台数、受注、稼働率、来店客数、会員数、利用者数、広告出稿額など。
  - **価格・採算指標**: 製品価格、スプレッド、原料価格、運賃、電力価格、金利、為替、販売奨励金、信用コストなど。
  - **政策・規制イベント**: 補助金、税制、関税、輸出規制、環境規制、薬価改定、料金改定、制度変更など。発表日・適用開始日・対象範囲・税率/補助額/規制値を残す。
  - **供給制約・サプライチェーン**: 半導体、部材、鉱山、物流、在庫、設備稼働、工場停止、認証問題など。会社影響が一次情報で未確認なら `業界論点、会社影響未確認` とする。
  - **会社固有プロダクト/案件名**: 新モデル、新工場、サービス名、OS/ADAS/プラットフォーム名、提携先、合弁会社名を、記事で固有名詞として使える形で整理する。
  - **競合・相対位置**: 主要市場シェア、競合販売台数、価格帯、店舗/拠点数、能力増強、比較対象企業のコード。公的統計・業界団体・各社一次情報を優先する。
- 会社開示または業界団体統計で市場シェア・販売数量シェア・能力シェア・顧客基盤シェアが確認できる場合は、`国内No.1` `業界大手` のような定性表現だけで終わらせず、具体的なシェア率・分母・時点を残す。記事冒頭の企業理解に使える場合は `記事冒頭で使用推奨` と明記する。
- 中計目標と比較するため、直近実績の財務基盤KPI（総資産、自己資本比率、ネットD/E、D/E、ROE、ROIC、営業CF、FCF、投資額、還元額など）を可能な範囲で取得する。目標値だけでなく、直近実績との差が分かる形で残す。
- 中期経営計画だけでなく、統合報告書・長期ビジョン・IR Day等に2030年、2035年、2040年などの段階目標がある場合は、`直近実績 -> 中計最終年度 -> 長期目標` の横比較表にできるように数値を保持する。
- 会社開示の感応度がある場合は、単に感応度を転記するだけでなく、3シナリオに使える `試算式候補` を残す。ただし会社開示でない組み合わせ試算は `Codex参考試算` `会社開示ではない` `前提付き` と明記し、結合条件と単独条件を混同しない。
- 市況連動・政策連動・金利連動・電力連動など外部環境の影響が大きい企業では、会社IRだけで閉じず、国際機関、業界団体、主要メディア、専門紙、調査会社の最新市況・需給見通しを補助指標として確認する。記事では会社IRを主根拠、外部指標を背景・確認指標として扱えるよう、出典名・時点・対象範囲を必ず残す。
- 不祥事、訴訟、行政処分、品質問題、内部統制、グループ再編、子会社削減などのガバナンス・構造改革イベントは、単なるリスク名で終わらせず、発生日/進捗、対象会社、件数、削減数、再発防止策、業績への直接影響の有無を確認する。
- 外部指標の参照優先順位は、(1) 会社一次情報、(2) 公的機関・中央銀行・規制当局・業界団体、(3) 取引所・国際機関、(4) 主要メディア/専門紙、(5) 調査会社推計、の順にする。
- 報道や調査会社しかない情報でも、複数ソースまたは業界構造から接続できる場合は、`推計` `報道ベース` `業界構造からの推定` と明記して記事本文に使ってよい。会社への影響が一次情報で確認できない場合でも、確度が `高` または `中` なら方向感・確認KPI・波及ラグは書く。金額インパクトの数値化は根拠がある場合に限る。
- `claude_input_pack.md` には、先行指標を必ず次の表で入れる。

| 指標カテゴリ | 指標名 | 現状数値 | 時点 | 出典 | 会社への効き方 | 波及ラグ | 記事での扱い |
|---|---|---:|---|---|---|---|---|
| 需要 | 例: HEV小売台数 | 例: 929千台 | 例: 2026年3月期 | 会社決算資料 | 四輪売上・モデルミックス | 0-1Q | 本文で使用 |
| 政策 | 例: 関税率 | 例: 10% | 例: 適用開始日 | 規制当局 | 四輪採算 | 即時-1Q | リスク表で使用 |

#### 不祥事・会計/統制・大型顧客変動
- 過年度訂正、不適切会計、内部統制上の重要な不備、業績修正、監査上の強調事項、主要顧客離脱、大型案件失注・終了を確認する
- 一次情報（適時開示、有価証券報告書、決算短信、会社IRニュース）で裏取りできたものだけ、事実として記載する
- 報道で見つかったが一次情報で確認できないものは「報道ベース、一次情報未確認」とし、記事本文には原則入れない
- 大型顧客・広告主・取引先の名称が非開示の場合、推測で社名を書かず「会社開示では名称非開示」と明記する

#### 投資・資本配分
- 設備投資、減価償却、研究開発費（年度別）
- M&A・出資（案件名、金額、持分比率、目的）
- 中期計画期間の累計投資額・配分

#### 中期経営計画
- 期間、目標年度
- 売上・利益・財務指標の目標値
- セグメント別の利益計画（年度別／少なくとも初年度＋最終年度）
- 戦略の3-5本柱と優先順位
- KPIマイルストーン
- 2030年、2035年、2040年など中計より先の長期目標がある場合は、短期会社予想・中計最終年度・長期目標を分けて整理する

#### 成長テーマ・新規事業
- 案件名、提携先、規模、進捗段階
- 投資額、想定収益貢献時期
- 量産・商用化に関するリスク

#### 競合比較候補
- 同業・隣接業種・同じ上流変数で比較できる企業を最低3社、推奨5社まで抽出する
- 競合候補は証券コード付きで、なぜ比較対象になるかを一文で残す
- 単一業態ではない企業の場合、広告、ゲーム、IP、金融、ECなど事業別に競合を分ける
- 伝統的な同業だけでなく、技術代替・ビジネスモデル代替・海外上場企業・非上場大手・顧客の内製化も確認する。例: 電子部品ではMEMS代替、半導体ではTSMC/OSAT/EDA、広告ではプラットフォーム内製、金融ではフィンテック代替。
- 代替プレイヤーは数値比較が難しくても、技術代替リスクや価格決定力を説明するために `代替リスク候補` として残す。記事本文で使う場合は「同業」ではなく「代替技術」「隣接競合」と明記する。
- 競合比較に使う数値は各社の一次情報を優先し、未取得の場合は「比較候補、数値未取得」としてClaudeに無理に記事化させない

#### 同業他社の同期決算サマリー
- 比較対象が明確な業界では、主要競合3-5社について、同じ会計期または直近同期の売上、営業利益、営業利益率、純利益、受注高/販売数量/会員数などの業種KPIを1表にまとめる。
- 競合数値は各社決算短信・決算説明資料・統合報告書など一次情報を優先する。速報報道や推計を使う場合は「報道ベース」「推計」と明記し、記事本文では過度に断定しない。
- 決算期がずれる場合は、対象期間を明記し、完全な横比較ではなく「直近開示ベース」として扱う。
- 競合比較表に入れる値は、Claudeがそのまま記事化できるよう、単位・会計基準・対象期間・出典URLを付ける。
- 競合比較が有用でない業態（独自事業構成、上場類似企業が少ない等）では、無理に表を作らず「比較困難な理由」を残す。

#### リスク要因
- 市況リスク（価格、為替、金利、原料）
- 規制・政策リスク
- 構造的リスク（需要減、競合増設、座礁資産）
- 個別案件リスク（特定設備、特定契約、特定地域）

#### サステナビリティ・人的資本
- CO2排出目標（Scope1/2/3、基準年）
- 気候関連リスクの認識（TCFD構成）
- 人的資本KPI（エンゲージメント、女性役職者、教育投資）

各業種で特に深掘りすべき項目。該当業種を担当する際は必ず確認。

| 業種 | 追加抽出項目 |

### 2.4 資料優先順位（資料種別ごとの主用途）

複数資料から同じ論点の数値・記述が取れる場合、**どの資料を最新・正として採るか**を以下の優先順位で判断する。

| 論点 | 第1優先 | 第2優先 | 補助 |
|---|---|---|---|
| 最新通期実績 | 決算説明資料 | 決算短信 | 有価証券報告書 |
| 通期会社予想・四半期進捗 | 決算説明資料 | 決算短信 | IR Press（業績修正時） |
| 長期文脈・サステナビリティ・人的資本 | 統合報告書 | 中期経営計画 | 有価証券報告書 |
| 中期経営計画の目標値・投資配分 | 中期経営計画 | 統合報告書 | 決算説明資料（補足スライド） |
| 成長案件・新規事業の進捗 | IR Press | 決算説明資料 | 報道 |
| セグメント・地域別の詳細内訳 | 有価証券報告書 | 決算説明資料 | 統合報告書 |
| 業界市況・先行指標 | 公的統計・業界団体統計 | 主要メディア報道 | 調査会社レポート（出典明示前提） |

- 第1優先資料に記載がない場合のみ、第2優先以降に降りる。
- 第1優先資料と矛盾する下位情報は採用せず、メモ側に「資料間の差異」として記録のみ残す。
- 統合報告書の古いスナップショット数値を最新実績として混在させない。古い資料を引用する場合は「**2025年時点**」「**中計策定時点**」などの時点を残す。

### 2.3 感応度の扱い（特に重要）

- 感応度は**会社開示の前提条件付き**として扱う。
- 「原油 +10ドル/バレル ＋ 為替 +5円/ドル の **結合条件** での影響」と「原油単独」「為替単独」の感応度は**別物**。資料に明示があるものだけ書く。
- 在庫影響あり／なし、タイムラグあり／なし、製品スプレッド込み／除く、の**区分を明確に**書く。
- 1要素感応度を組み合わせて多要素シナリオを作る試算は、必ず「**会社開示ではなく試算**」と明記する。
- 会社が感応度を非開示の場合は、`会社感応度は非開示` と明記する。その上で、記事の補助材料として必要な場合のみ、公開済みの地域別売上・外貨建売上・資産残高・平均価格・販売数量などから `Codex参考試算` を作ってよい。
- 参考試算には、計算式、仮定、対象範囲、単位、丸め、限界を必ず書く。例: `参考試算: 海外売上7,000億円に対し、1ドル=10円の円高を単純換算した売上影響。実際のヘッジ、現地費用、通貨構成は未反映。`
- 参考試算は本文の主張の根拠にしない。表や注記で「規模感を見るための概算」として扱い、会社計画や会社感応度と混同しない。

## 3. `claude_input_pack.md` の標準構成

以下のセクションを順に並べる。

1. **Claudeへの依頼文**（記事の目的・守ること・出力フォーマット）
2. **基本情報**（企業名、コード、市場、業種、Sector、会社概要、売上規模、主要事業基盤、記事タイトル案、スラッグ案、キーワード案）
3. **統合結論**（Codex側で考えた、業績を一言で要約・短期/中長期の構造分け）
4. **Codex直接PDF要約**（`pdf_summary.md` の主要部を貼り付け or 参照リンク）
5. **Web補足情報**（会社プレスリリース、IRページから引いた追加情報。**必ず出典URL付き**）
6. **記事構成案**（H2/H3単位の骨子。指示書の必須見出しを満たすこと）
7. **表に入れるべきデータ**（業績表、セグメント表、先行指標表など）
8. **禁止・注意表現**（NG例／OK例ペアで）
9. **参照リンク候補**（記事末尾に貼る一次情報URL）
10. **非AIグラフ/数値図表候補**（Claudeが記事化時に必要性を判断し、Codexが機械的に作成できる候補）

Claudeへの依頼文には、表作成方針として以下を必ず含める。

- 実績・会社予想・中期経営計画・Visionなど複数時点を比較する表は、横軸を期間、縦軸を指標にする
- `2026年3月期売上高` `2027年3月期売上予想` `Vision2030売上高` のように、期間名と指標名を第1列へ混ぜた `項目/数値/注記` 表は避ける
- 期間別に比較できない単独KPIは、無理に同じ表へ押し込まず、注記または別表で扱う
- 数値グラフ化しやすいデータ（売上構成、利益増減、営業利益内訳、中計ロードマップ、感応度、先行指標推移など）は、Claudeが「記事に入れると理解が進む図表候補」として選べるよう、数値・単位・時点・出典を揃えて渡す。

### 3.1 非AIグラフ/数値図表候補の書き方

生成AI画像は「上流環境と業績への波及」のような概念図に使い、正確な数値を読ませるグラフには使わない。Codexは `claude_input_pack.md` に、以下の形式で非AIグラフ候補を残す。

```md
## 非AIグラフ/数値図表候補

| 候補 | 目的 | 元データ | 推奨形式 | 挿入候補位置 | 注意点 |
|---|---|---|---|---|---|
| セグメント別売上構成 | 事業規模の偏りを一目で見せる | 2026年3月期 セグメント別売上高 | 横棒グラフまたは100%積み上げ | H2-2 収益構造 | 合計との整合確認 |
| 営業利益増減要因 | 一過性と本業の区別を見せる | 前期営業利益、増減要因、当期営業利益 | ウォーターフォール | H2-3 業績の全体像 | 会社開示の増減要因だけ使う |
```

Claudeは記事作成後、`claude_review_notes.md` に「採用推奨」「不要」「Codexで作成候補」の判定を残す。Codexはその提案を読み、必要なものだけ数値検証してHTML/CSS/SVG/PNGとして作成・挿入する。

### 3.2 「禁止・注意表現」セクションの作り方

業種固有の誤読パターンを洗い出して、各企業ごとに最低3-5個のNG/OKペアを書く。

例（石油業界）:
```
- NG: 原油価格が上がれば必ず利益が増える。
- OK: 原油価格上昇局面ではタイムラグ寄与でプラスの場合が多いが、需要弱含み・在庫評価の動きも同時に見る必要がある。
```

例（半導体）:
```
- NG: 受注が増えたから来期は増収増益。
- OK: 受注増は2-4四半期先の売上に効くが、価格改定や歩留まりにより利益増は別途要確認。
```

## 4. 数値・出典管理ルール（厳守）

### 4.1 出典の付け方

- 各PDFから抽出した数値の末尾に、最小でも資料名（`(決算説明資料)`）、可能ならページ参照（`(決算説明資料 p.12)`）を付ける。
- 数値が複数資料に登場する場合、**資料間の差異も記録**（例: 「2024年度純利益は決算説明資料で1,041億円、統合報告書では在庫影響除き1,248億円」）。

### 4.2 「資料非開示」の明示

- 会社一次資料で数値を出せないものは**「会社資料では非開示」**と明記する。ただし、外部統計・業界資料・競合資料から確度高く推定できる場合は、空欄で終わらせず `外部統計ベース` `筆者推定` `レンジ推定` として別枠で残す。
- 業種上重要で、今回の資料に無いものは「会社資料では非開示。ただし外部統計/業界構造から推定可能か要確認」と注釈し、記事価値が高い場合は追加調査対象にする。

### 4.3 会計基準・定義変更（メモ／記事の使い分け）

- 会計基準（日本基準／IFRS／米国基準）の確認は**メモには必ず記録**する。年度対応表に「会計基準」列を含めて完全に残す。
- 公開記事での明示は**読者の比較判断に影響する場合のみ**に絞る。具体的には以下のいずれかに該当する場合:
  - IFRS／米国基準への移行や任意適用の開始（例: 出光興産がFY2026からIFRS任意適用）
  - 同期間内で複数基準が混在（例: 海外子会社のみIFRS）
  - 利益指標の定義変更（例: 「営業利益＋持分法投資損益」→「金融費用除き税引前損益」）
  - 過年度との単純比較が不可になる事象
- 上記に該当する場合は、**該当期と新旧定義を年度対応表で示し、「単純比較不可」を本文に明記**する。
- **日本基準のまま通常運用している会社**では、記事内で「日本基準」を過度に強調しない。年度対応表に「会計基準」列を入れる必要はなく、決算月の特殊性（3月決算以外）や対象期間の説明を優先する。免責文や注記でも「全期間とも日本基準」のような冗長な明示は避ける。

### 4.4 一次情報優先

- 数値の信頼順位は: **PDF直読（会社開示） > 会社プレスリリース > IRページ > 主要メディア報道 > 業界調査会社レポート**。
- 上位の情報源と矛盾する下位情報はメモから外す。残す場合は「報道情報、未確認」とラベル。

### 4.5 Make要約の排除

- Make等で過去に作られた要約は**入力にしない**。Codex自身がPDFを開いて読む。
- 過去のMake要約がシートにある場合も、参考閲覧に留め、`pdf_summary.md` には流用しない。

### 4.6 「資料非開示」のメモ／記事使い分け

「資料非開示」「未開示」「資料内記載なし」は**メモには漏れなく残す**が、**公開記事ではそのまま並べない**。読みづらく、信頼を損なう。

- **統合分析メモ**（内部資料）: 全数値・全項目について「資料非開示」を含めて完全に残す。後続レビューと次期更新の手がかりになる。
- **公開記事（HTML）**: 「資料非開示」が多発する箇所は、以下のいずれかに丸める。
  - 自然文で言い換える（例: 「電子材料の販売数量・単価は会社非開示」 → 「電子材料の数量・単価は開示されていないため、本記事では潤滑油の単価改善寄与を中心に扱う」）
  - 該当行を表から削除し、開示されている範囲だけで表を成立させる
  - 重要な非開示は脚注に1回だけ残す（複数箇所で繰り返さない）
- **断定回避と「資料非開示」明示は両立させる**: 「世界唯一」「業界トップ」のような表現は使わないが、「資料非開示」とだけ書いて済ませず、記事では何が分かって何が分からないかを読み手に伝える。

## 5. PDF抽出時の標準ワークフロー

1. シート該当行のPDF URLを列挙し、`pdf_summary.md` 冒頭の対象資料リストに記録（取得日も）。
2. 各PDFを直接ダウンロード→本文抽出（PDF→テキスト）。スキャン画像系の場合はOCR。
3. 上記2.1の必須抽出データを順に拾う。チェックリスト形式で「○／△（部分開示）／×（非開示）」を内部メモしておくと漏れ防止に有効。
4. 業種特定後、2.2の業種別ヒントから追加抽出する。
5. PDF内の数値から、会社固有の**業績ドライバー仮説**を作る（例: 原油タイムラグ、製油所稼働率、石炭価格、受注残、ARPUなど）。
6. Make旧フローのPDF要約プロンプトと同じく、要約を短くしすぎない。KPI、市場環境、リスク、競合、顧客/取引先、成長テーマ、業績予想に必要な素材は、記事に使うか未定でも残す。
7. ドライバー仮説に基づき、統合メモ作成前に必要な**外部先行指標**を取得する。Makeのように統合メモ後に抽出してもよいが、Codex/Claude Code運用では「PDF要約→ドライバー仮説→先行指標取得→統合メモ」の順を標準とする。
8. **Make式ギャップ検索**を行う。各ドライバーについて、以下が空欄なら追加確認する: 上流市場規模、需要指標、価格/採算指標、政策・規制イベント、供給制約、会社固有プロダクト/案件名、サービスKPI、開発体制/能力、競合比較、業績を歪める一時要因、不祥事/会計訂正/大型顧客変動。
9. 3行サマリーは**最後**に書く。本文と外部先行指標を確認してから論点を凝縮する。
10. `claude_input_pack.md` を組み立てる。記事構成案・表データ・禁止表現は Codex 側で **事前に下書き**して Claude の作業を軽くする。
11. 最後にチェックリスト（下記6章）で漏れと矛盾を確認。

### 5.1 先行指標取得のタイミング

統合メモ作成前に先行指標を取得してよい。むしろ、PDF直読で業績ドライバーが明確になった後に取得することで、Claudeが統合メモと記事本文に外部数値を自然に織り込める。

標準順序:

```
PDF直読
→ 業績ドライバー仮説
→ 必要な先行指標リスト化
→ Web/Serper/公式統計/業界資料で数値取得
→ claude_input_pack.md に Web補足情報として格納
→ Claudeが統合分析メモ・記事本文を作成
```

注意点:

- PDFを読む前にWeb検索を始めない。先に検索すると、会社固有でない一般論や不要なニュースが混ざりやすい。
- 外部先行指標は、会社開示より下位の補足情報として扱う。会社開示と矛盾する場合は会社開示を優先する。
- 取得した外部指標には必ず出典URLと確認日を付ける。
- 速報値・報道値・調査会社推計は「報道ベース」「推計」などのラベルを付け、会社実績と混同しない。
- 先行指標が取得できない場合は、空欄にせず「取得不可」「資料非開示」「有料情報のみ確認」など理由を残す。
- Claudeに「情報が足りない」と言われやすいのは、固有名詞と外部数値が不足しているケース。会社公式資料に出ている新製品名、規制名、政策名、モデル名、提携先名、地域名、競合名は、記事で使うか未定でも `claude_input_pack.md` に残す。
- ただし、外部数値を増やすほど誤情報リスクも上がるため、`記事で使う` `内部補助` `使わない/要確認` の3区分を各指標に付ける。

例（石油・ガス）:

- ドバイ原油、WTI、Brent
- 豪州一般炭、Newcastle coal
- USD/JPY

### 業界難用語の初出説明ルール

- 記事の理解に不可欠な業界難用語・会計難用語・業種固有KPIを**2〜4語だけ**選ぶ。
- 対象は、業界外の読者が初見で意味を取りにくく、かつ業績ドライバー理解に必要な語に絞る。例: 在庫影響、タイムラグ、精製マージン、白油、受注残、粗利率、Cap Rate、WFE、DRAM、光トランシーバ、MEMS、DOE、ROIC、NIM、AUM、ARPU。
- 選んだ語は、その語が本文で初めて本格的に使われた直後に `<div class="beginner-box term-box">` で説明する。
- CSSは既存の `beginner-box` を効かせるため `beginner-box term-box` とする。`term-box` は役割識別用の追加クラスで、見た目を変えたい場合の将来拡張に使う。
- 用語解説型ボックスを参照資料前・記事後半・用語集にまとめて置かない。読者が最初に詰まる場所で解く。
- 冒頭の1行サマリー、definition-lead、summary-boxだけに用語が先に出る場合でも、本文で初めて詳しく扱うセクション内の初出直後に置く。
- すべての専門語を解説しようとして辞書化しない。用語解説boxは記事全体で2〜3個までを目安にし、軽い語は本文中の括弧補足で済ませる。
- 見出しは `<p><strong>📘 用語メモ：在庫影響とは</strong></p>` のように、対象語が一目で分かる形にする。
- `💡 ワンポイント解説` は、誤読防止・因果の噛み砕き・論点理解の補助として残す。難用語そのものの説明は `📘 用語メモ` に分ける。

#### 非AIグラフ/数値図表の追加フロー

AI生成の上流環境マップとは別に、記事の説得力を高めるため、必要に応じて**非AIグラフ/数値図表**を追加する。

- Claudeは記事作成時に、読者理解に効く図表候補を `claude_review_notes.md` に残す。例: セグメント別売上構成、営業利益増減要因ウォーターフォール、会社計画の利益内訳、中期経営計画ロードマップ、感応度整理、主要KPI推移。
- Claudeは候補の**目的・挿入位置・使うべき元データ・注意点**まで書く。数値グラフそのものは作らない。
- CodexはClaudeの候補を読み、一次資料・PDF要約・Claude投入パックで数値を再確認する。
- 採用する図表だけを、HTML/CSS/SVG/PNGのいずれかで機械的に作成する。正確な数値を読ませる図は、生成AI画像では作らない。
- 記事内では、非AIグラフ/数値図表を「数字を信頼して理解する図」、AI生成の上流環境マップを「因果構造を直感的に掴む図」として役割分担する。
- 企業分析記事では、FICの強みである「上流環境の変化が企業業績へどう波及するか」を必ず可視化する。画像は役割を分ける。
  - **上流環境と業績への波及イメージ**: 生成AI画像で必須作成する因果図。上流環境→先行指標→企業への効き方→業績への波及を、業績ドライバー章の冒頭またはドライバー①直前に置く。
  - **上流環境メインのマップ**: `H2 上流環境と先行指標` 内の `H3 上流環境マップ` 直下に置く。マクロ、需要、地政学、政策、技術、競争環境など、業績の前提となる外部環境そのものを俯瞰させる。こちらは因果図と重複させず、「いま何が外部環境として効いているか」を整理する。
- 挿入する図表は増やしすぎない。標準は0〜3点、最大でも4点までを目安にし、本文の読みやすさを優先する。4点入れる場合も「読者の理解が明確に進む重要図表」に絞る。
- 同じH3の中に同じ論点を説明する図表を複数入れない。例えば「2027年3月期見通しの内訳」を説明する図表は、ウォーターフォールか構成比のどちらか重要な1枚に絞る。図表は対応するH3の内側、原則としてH3見出しの直後または該当表の直前に置く。
- 図表は、本文から切り離して見ても意味が分かるようにする。タイトル、短い説明文、軸・単位・時点、出典、注記を必要最小限で入れ、読者が「何を見る図か」「何が重要か」を画像単体で理解できる状態にする。
- 図表は「理解してほしい重要論点」を伝えるために入れる。単なる表の画像化にしない。タイトルまたはサブタイトルには、読者に伝えたい結論を入れる（例: 「一過性利益と本業を分けて見る」「上位3区分で利益の大半を占める」「国内縮小を海外で補う」）。何を伝えたいかが曖昧な図表は作らない。
- 作成後は必ず画像を目視確認し、文字の重なり、ラベルのはみ出し、凡例とグラフの衝突、数値単位の欠落がないか確認する。文字が読みにくい場合は、要素数を減らす、ラベルを外側に逃がす、説明文を短くする、余白を広げるなどして修正してから挿入する。
- 採用/不採用の判断は `claude_review_notes.md` の `Codexレビュー結果` に残す。

#### 画像生成ルール

- 画像は記事本文をもとに**ゼロベース生成AI画像**として作る。会社ロゴ、実在写真、IR図表の模写、第三者著作物の再現は避ける。
- 企業分析記事の標準画像は、**「上流環境と業績への波及」インフォグラフィック**とする。抽象的なイメージ画像ではなく、読者が「何が変わると、どの先行指標が動き、企業業績へどう波及するか」を一枚で把握できる図解にする。
- 売上高・営業利益・セグメント利益・構成比など、正確な数値を読ませる図は生成AI画像で作らない。これらは「記事内図解画像」ではなく「数値グラフ」として扱い、表データから機械的に作るHTML/CSS/SVG/PNGを使う。
- 数値グラフは、AI生成の上流環境マップを置き換えるものではない。役割は別で、上流環境マップは因果構造、数値グラフは売上規模・利益貢献・推移を見せるために使う。
- 数値グラフをPNGとして作成・アップロードした場合も、元データ表と作成スクリプトまたは作成メモをローカル作業フォルダに残し、`AY` に同じフォルダのフルパスを保存する。
- 既存方針の原則: **画像は装飾ではなく、企業単体の業績ドライバー構造を理解するための図解**。ただし新フォーマットでは、単なる社内ドライバー表ではなく、FICの中核である**上流環境 → 先行指標 → 企業への効き方 → 業績への波及**を標準軸にする。
- 16:9横長を標準。WordPress本文幅で見ても構造が分かるよう、太い見出し・太い矢印・色分けされた行・大きめのアイコンを使う。
- 標準フォーマットは以下の4列構成とする。
  - 左端: ドライバー番号と名称（例: `1 原油タイムラグ`）
  - 1列目: `上流環境`
  - 2列目: `先行指標`
  - 3列目: `企業への効き方`
  - 4列目: `業績への波及`
- 行数は原則4行。記事で重要な上流要因・先行指標の組み合わせを4つに集約する。5つ以上ある場合も、画像では重複を避けて4本に圧縮する。
- 各行は色分けする。推奨は、1行目ネイビー、2行目ティール、3行目グリーン、4行目ゴールド。リスク帯は最下部に赤で配置する。
- 画像は**単体で意味が通じること**を必須条件とする。雰囲気だけの図、アイコンだけの図、枠内に説明文がない図は不採用。記事本文を読まなくても、画像だけで「上流環境 → 先行指標 → 企業への効き方 → 業績への波及」の因果が追えるようにする。
- 画像生成前に、必ず下記の参考フォーマット画像を目視する。記憶や文章説明だけで作らず、「カード内に主ラベル・図像・下部コメント帯が入っているか」を参考画像と横並びで確認してから採用判断する。
- 各カードには必ず**大きな主ラベル**を入れる。さらに、参考画像のようにカード下部へ**短い補足帯（コメント帯）を必ず置く**。これは任意ではない。主ラベルだけでは伝わらない接続関係を補うため、各カードを `上部の主ラベル + 中央の図像 + 下部の短い因果コメント帯` の3層構成にする。
  - 主ラベル例: `原油市況・為替`、`仕入価格と在庫`、`タイムラグ損益`、`利益が大きく振れる`
  - 補足帯例: `ドバイ原油・USD/JPY`、`調達から販売まで時間差`、`価格上昇局面はプラス`、`短期利益の最大変動要因`
- **枠内コメント帯がない画像は不採用**。タイトル、列見出し、セルの主ラベル、数値、アイコンが揃っていても、各カード下部のコメント帯がない場合は90点基準未満として再生成またはCodex側で作り直す。
- 画像内テキストは**短い日本語ラベル + 最小限の補足語**にする。細かい文章・長文・複雑な表は避けるが、枠内の文言を省略しない。数値を入れる場合は記事本文と整合する主要数値だけに限定し、誤読される略記を避ける。
- 生成AIは日本語文字を誤る場合があるため、完成後に必ず目視で確認する。誤字、文字崩れ、誤数値が目立つ場合、または枠内テキストが欠落している場合は再生成する。許容できない場合は、AI生成画像を採用せず、Codex側で図解PNGを作成する。
- 画像自体を目視し、**90点基準**で判断する。`AW=完了` は品質保証ではなく、画像の構造・文字・数値・見栄えを確認してから完了にする。

- 企業分析記事で使う主なモチーフは以下。
  - 事業ドライバー構造（例: 原油・為替・稼働率・資源価格が企業利益へ流れる）
  - 主要事業ポートフォリオ（例: 燃料油、資源、高機能材、CNX）
  - 上流環境マップ（例: マクロ、業界構造、政策、技術、地政学）
- 画像プロンプトには「会社名・証券コード・主要ドライバー・避ける要素」を明記する。
- プロンプトには「reference imageと同じフォーマット」「Japanese corporate infographic」「4 horizontal rows」「4 rounded panels per row」「large Japanese text inside every panel」「short explanatory strip at the bottom of each panel」「upstream environment to leading indicators to earnings impact」「bottom red risk band」「crisp and legible Japanese text」を明記する。

#### 挿入ルール

- 挿入位置は原則として、最初の個別ドライバー見出しの直前にする。例: `ドライバー①`、`売上ドライバー①`、`ドライバーA` の直前。
- 記事構成上、個別ドライバー見出しがない場合のみ、H2「業績ドライバー」章の冒頭説明直後、または最初の `<h2>` の直前を代替位置にする。
- 画像HTMLは以下の形を標準にする。

```html
<figure class="article-image company-driver-map">
  <img src="WORDPRESS_MEDIA_URL" alt="出光興産（5019）の業績ドライバーを示す図解" loading="lazy" decoding="async">
  <figcaption>出光興産の業績ドライバー構造</figcaption>
</figure>
```

- 画像本文挿入時の `figure` クラスは、既存記事（ホンダ7267）と同じ **`article-image company-driver-map` 固定** とする。`fic-article-image`、`fic-driver-map`、`fic-upstream-impact` などの独自クラスは使わない。独自クラスにするとWordPress側のbox表示CSSが効かず、画像が通常画像として表示される。
- すでに同種の `figure.article-image` がある場合は重複挿入しない。差し替える場合は既存figureを置換する。
- `AX` に画像挿入済みHTMLを保存し、WordPress更新には `AX` を使う。

#### WordPress更新・シート反映

1. `AW=作成中` に更新。
2. WordPressへ本文を反映する前に、必ず企業分析シートの `AM` を確認する。
   - `AM` に投稿IDがある場合は、そのIDを更新対象として固定する。新規投稿は作成しない。
   - `AM` に投稿IDがある場合は、スラッグ検索・タイトル検索で別投稿が見つかっても `AM` のIDを優先する。投稿IDとスラッグが食い違っていても、勝手に slug を修正しない。必要なら `AS` に差異メモを残す。
   - `AM` が空欄の場合だけ、`G` 列のスラッグ、証券コード、会社名でWordPress既存投稿を検索する。既存投稿が見つかったら、その投稿IDを `AM` に保存してから既存投稿を更新する。
   - `AM` が空欄で、かつWordPress側にも既存投稿が見つからない場合に限り、下書きを新規作成し、返却された投稿IDを `AM` に保存する。
   - 更新直前と更新後に、反映先の投稿IDが `AM` と一致していることを確認する。誤って重複下書きを作成した場合は、公開前に重複投稿と未使用メディアを削除する。
3. 画像を生成し、WordPressメディアへアップロードする。
4. WordPressメディアURLを使って `AL` にfigureを挿入し、`AX` に保存。
5. `AX` を使って、手順2で確定した投稿IDを更新する。新規作成は手順2で「既存なし」と確認できた場合だけ行う。
   - 既存投稿更新時は、本文・タイトルなど必要項目だけを更新し、**スラッグとアイキャッチ画像は変更しない**。
   - 新規投稿時のみ、`G` 列のスラッグを使用する。`G` 列が空の場合だけ、企業名・コードからスラッグを作成して `G` 列へ保存する。
   - 一度決めた `G` 列のスラッグは以後変更しない。投稿IDとスラッグが食い違っていても、投稿IDを優先し、勝手に slug を修正しない。必要なら `AS` に差異メモを残す。
   - 画像挿入用にアップロードした本文内図解は、**アイキャッチ画像には設定しない**。アイキャッチを変更するのは、ユーザーが明示的に画像ファイルまたはWordPressメディアIDを指定した場合に限る。
6. `AN=WP反映完了（画像挿入済みHTMLで更新）`、`AW=完了`、`AP=完了`、`AQ/AR=更新日` にする。
7. 画像を作成したら、そのタイミングで `AY` に画像格納フォルダを**フルパス**で保存する。X投稿スケジュールを企業分析シート内で管理するため、画像URLだけでなく、ユーザーがエクスプローラーでそのまま開けるローカル作業フォルダも残す。`AW=完了` にする前に `AY` が空欄でないことを確認する。
8. `AS` に「画像生成・挿入・WP更新済み。画像URL: ...」を追記する。

#### WordPressメディア整理ルール

- WordPressへアップロードした本文内図解のうち、最終的に記事本文の `AX` で参照していない画像は削除する。
- 画像の初稿、不採用版、差し替え前の旧版、重複下書き作成時にアップロードされた画像は、採用画像の反映確認後にWordPressメディアから削除する。
- 削除前に、対象画像URLが現在の `AX` HTML、WordPress本文、X投稿予定、動画作成予定で使われていないことを確認する。
- ローカル作業フォルダの生成履歴は残してよい。ただしWordPressメディアライブラリには、公開記事や今後の投稿で使う画像だけを残す。
- 重複投稿を誤って作成した場合は、重複投稿だけでなく、その重複投稿用にアップロードした未使用画像も削除する。

### 7.3 アイキャッチ画像の扱い

本文内の図解画像とアイキャッチ画像は別物として扱う。記事更新のたびにアイキャッチが変わると、SNS表示・OGP・記事一覧の見た目が揺れるため、既存投稿更新時はアイキャッチを変更しない。

#### アイキャッチ更新ルール

- 既存投稿更新時は、**原則として `featured_media` を送信しない**。
- アイキャッチ画像はユーザー作成を標準とする。Codexは原則としてアイキャッチを生成しない。
- アイキャッチを変更するのは、ユーザーが明示的に画像ファイルまたはWordPressメディアIDを指定した場合に限る。
- 本文内図解、上流環境マップ、業績波及図はアイキャッチに流用しない。
- 新規投稿でアイキャッチ未設定の場合も、ユーザー作成画像がない限り未設定のままにする。

### 7.4 品質改善ループ（レビュー結果を仕様へ戻す）

FIC企業分析フローでは、1社ごとのレビューで見つかった不足を、その場限りの修正で終わらせない。汎用化できる不足は `docs/codex_company_analysis_pack_spec.md` または `docs/claude_integrated_memo_lessons.md` に戻し、次回以降の企業で同じ不足を繰り返さない。

#### 基本方針

- Claudeが `claude_review_notes.md` に残した「Codex入力で不足していた情報」「判断に迷った点」「一次情報で要確認の項目」は、Codexレビューの最初に必ず読む。
- Codexは各項目を、以下の4分類で処理する。
  - `確認済み`: 一次情報で確認し、記事修正不要または修正済み。
  - `追加抽出済み`: PDF要約/投入パックへ追加し、ClaudeまたはCodexで記事へ反映。
  - `記事側で再修正`: Claudeに再生成/修正を依頼する必要がある。
  - `据え置き`: 一次情報で確認できない、または記事に入れると過度な推測になるため採用しない。
- その企業固有の話で終わる項目と、他社にも再利用できる項目を分ける。
- 他社にも再利用できる項目は、必ず「汎用プロンプトへ反映すべき事項」として `claude_review_notes.md` の `Codexレビュー結果` に残す。
- 反映が必要な場合は、同じ作業ターン内で仕様書へ追記する。時間がない場合でも、`Codexレビュー結果` に「仕様書追記候補」として残す。

#### `claude_review_notes.md` 末尾に追記する標準形

```md
## Codexレビュー結果

### 処理結果
- 確認済み:
- 追加抽出済み:
- 記事側で再修正:
- 据え置き:

### 汎用プロンプトへ反映すべき事項
- 例: ゲーム・エンタメ企業では、WAU/MAU/DAU、有料会員、海外提供タイトル数、開発体制人数、上流市場規模を必須確認にする。
- 例: 広告事業を持つ企業では、広告主数、媒体連携数、大型顧客離脱、動画広告市場を必須確認にする。
- 例: 過年度訂正・不適切会計・内部統制は、有報と適時開示で必ず検索する。

### 今回限りの個別対応
- 例: Cygamesスタッフ数は公式採用サイトで確認した数値のみ採用し、未確認数値は使わない。
```

#### 仕様書へ戻す判断基準

次のいずれかに該当する場合は、汎用ルールとして仕様書へ反映する。

- 同じ業種の別企業でも起きそうな不足。
- 会社固有ではなく、業種KPI・市場規模・競合比較・リスク確認の抜け。
- 数値誤読、単位変換、年度対応、会計基準、感応度、顧客/案件例の区別など、再発すると記事品質を大きく落とすもの。
- Make旧フローでは拾えていたが、Codex/Claudeフローで抜けたもの。
- Claudeが記事作成時に迷ったが、Codex側の準備で解消できるもの。

#### 反映先の目安

| 反映先 | 反映する内容 |
|---|---|
| `docs/codex_company_analysis_pack_spec.md` | CodexがPDF要約・Web補足・Claude投入パック作成時に追加で集めるべき項目 |
| `docs/claude_integrated_memo_lessons.md` | Claudeが統合メモ・記事を書くときに守るべき表現規律、誤読防止、構成ルール |
| `wordpress/templates/company_analysis_template.html` | 記事HTMLの構成、挿入ブロック、FAQ、関連銘柄/関連テーマなどのテンプレ変更 |
| `scripts/` | シート更新、WordPress更新、URL確認、PDF抽出など機械化できる作業 |

#### 運用例

- CyberAgentで「上流市場規模が薄い」と判明した場合:
  - その場で国内動画広告市場、モバイルゲーム市場、アニメ産業市場を追加取得。
  - ゲーム・エンタメ業種の追加抽出に、上流市場規模、WAU/MAU/DAU、海外提供本数、開発体制を追加。
- 出光興産で「感応度の結合条件が崩れやすい」と判明した場合:
  - 石油・ガス業種の追加抽出に、感応度の結合/単独/在庫影響区分を明示。
  - Claude側規律に、会社開示の感応度条件を勝手に分解しないルールを追加。

## 8. Codex以外の関係者向けメモ

- **Claudeは入力資料の範囲を超えて推測しない**。資料に無い数値は記事に書かれない。だから Codex 側の準備の厚みがそのまま記事の厚みになる。
- **Make要約は使わない**前提のため、Codex が PDF を直読する工数が必要。テンプレ化・スクリプト化が今後の効率化の鍵。
- **特殊論点（IFRS移行、定義変更、感応度の結合条件など）はCodex側で先に整理**しておくと、Claude が記事内で混乱しない。
- **レビューで見つかった不足は仕様へ戻す**。1社で発見した不足のうち汎用化できるものは、次回以降の企業で最初から取得できるようにする。
